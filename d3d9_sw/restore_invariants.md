# Restore invariants

What must be true immediately after a restore, expressed as checks we can
actually run, so that a broken restore is *detected* at the restore rather than
diagnosed from a crash several frames later.

Nothing here is built except where it says BUILT. Every number quoted as measured
comes from `d3d9_sw_savestate.txt`, `d3d11_sw.log` or harness output on
2026-08-30 and 2026-08-31; anything estimated is marked as such.

## Why this document exists

Eight distinct failures have been chased so far. Six of my explanations for them
were wrong, and three of those were wrong in the same way: I named a plausible
mechanism, built the fix, and only then measured whether the mechanism was
present. Two of the "facts" the theories rested on turned out to be produced by
my own instruments - a phantom 18-second save from a stale timestamp, and a
100-cycle clean run produced by a blacklist that had quietly removed whatever the
failure touched.

The pattern is not bad luck. It is that a crash arrives late, far from its cause,
already mixed with the consequences of the damage, and by then the only tool left
is a story. An invariant check arrives at the moment of damage and needs no
story.

So the goal is a finite checklist, not a better theory. A restore either satisfies
the checklist or it does not, and the checklist is the thing that gets extended
when a new failure appears.

## The classes are generated by the boundary, not by Mono

It is tempting to write this as "invariants of Mono 2018.4.15 / bdwgc", and that
framing is half wrong. Every byte in the process is rewound except our own
exclusions and memory the OS keeps outside the snapshot. An inconsistency after a
restore can therefore arrive in exactly three ways, and the list is closed:

**Class A - outward straddle.** Something inside the snapshot refers to something
outside it. The reference is put back to its save-time value; the target has moved
on.

**Class B - inward straddle.** Something outside the snapshot refers to something
inside it. The reference stays in the present; the target is rewound underneath
it. This is the direction we have barely examined, and it is where the current
unexplained failure most likely sits.

**Class C - captured mid-mutation.** Both halves are inside the snapshot, and the
structure was inconsistent at the instant of capture. No boundary can be moved to
fix this one, which makes it categorically different from A and B: the only repair
is not to take the picture at that moment.

Mono decides *which* structures fall into which class and how loudly each one
fails. It does not decide the classes. That matters because a checklist organised
by class survives a Unity upgrade, while a checklist organised by Mono internals
does not.

### Confirmed instances, by class

**Class A.** `ntdll!RtlpDynamicFunctionTable`, the growable unwind tables Mono
registers for JIT-compiled code. The list head is in ntdll's image data, which no
setting of `D3D9SW_REWIND_GAMEHEAP` or `D3D9SW_REWIND_SWHEAP` has ever rewound;
the entries are heap blocks that are rewound. Failed as
`FAST_FAIL_CORRUPT_LIST_ENTRY` inside `RtlAddGrowableFunctionTable`. This is the
one that explains why four different heap configurations could not possibly have
helped. FIXED by record-and-replay around the restore.

**Class A.** The game holding a COM pointer into our own memory across a restore
- confirmed on an `ID3D11Query`, which was released and then used after a restore
put the game's pointer back. FIXED by object retirement: the header and vtable
stay alive, only the payload is freed.

**Class C.** `jit_info_table_copy_and_split_chunk` incrementing a refcount
through a pointer read out of a partially-filled chunk array. Proved from the
live debugger rather than inferred: the two tables differed by exactly one chunk
(0x17d against 0x17c) with identical `num_valid` and byte-identical leading chunk
pointers, and the faulting index was 281 of 380 - in bounds, with indices 0-5
sane. A fill loop was photographed halfway through. MITIGATED by the settle
check, which is coarse (whole module) and expensive under load (1178-1462 ms of
suspend time when the JIT is hot, against 34-83 ms when it is quiet).

**Class B, named but not acted on.** Eight blocks on the game's rewound heap are
held by system thread TEBs, reported in every session. TEBs are not in the
snapshot; those blocks are. This is the cheapest identified win in the whole
project and has been deferred four times.

### Instances that were theorised and then measured absent

Recorded because a falsified theory is a result, and because the cost of
forgetting one is rebuilding it.

**Held critical sections.** The theory: a `CRITICAL_SECTION` captured while held
comes back held, owned by a thread whose release was rewound, so every later
entry takes the contended path - and the contended path is where a harness fault
landed. BUILT: tracking of `InitializeCriticalSection` / `AndSpinCount` / `Ex` /
`DeleteCriticalSection` across every module, with reinitialisation of sections
that came back held and whose owner is not among the restored threads. MEASURED:
314 sections tracked through 51 redirected imports, and every restore reports
zero came back held and zero reinitialised. The repair does nothing and the crash
is unchanged.

Caveat, so this is not overstated: only 11 of the 314 were live *and* inside the
restored region set, and sections created inside Mono's `DllMain` - before any
hook can be installed - are invisible by construction. "None came back held" is
weaker evidence than 314 suggests.

**Mid-mutation capture as a sufficient cause.** 120 harness cycles, 109 of which
caught a fill loop mid-flight, produced zero bad restores. Catching a writer
mid-update is survivable on its own, because the restore rewinds the writer too
and it redoes the work. So the OSFE instance needs a second ingredient, and the
leading candidate is that the writer does not resume - a restore has reported 52
threads against 55 at save.

**Concurrency as a required ingredient.** Withdrawn. With the harness blacklist
disabled, one worker and four workers fail at identical rates (4 clean / 2
crashed out of 6 each). The earlier "1 worker = 100/100 clean" result was
produced by a poisoned control.

## The invariants

Ordered by cost, cheapest first. Each states what is checked, through what, and
what a failure would mean.

### 1. The Mono runtime still works - BUILT, FIVE ORACLES, ALL GREEN

All five ask through exported functions only, so none of them needs a struct
layout and none can rot silently at a version change. All five were confirmed
present in the game's own `mono-2.0-bdwgc.dll` before being written, with a
deliberately made-up symbol name as a negative control to prove the search
worked.

**1a. The JIT info table is complete and correctly attributed.** Every method
compiled before the save is still findable through `mono_jit_info_table_find`,
and `mono_jit_info_get_method` returns the same `MonoMethod`. MEASURED green on
every restore. Note what it does *not* ask: whether the code runs. Only whether
it can be found.

**1b. Per-thread managed identity, i.e. does the TLS restore work.** Mono keeps
the current `MonoThread` in thread-local storage, and the load has always
reported "N context(s) restored, N with TLS" with nothing checking the claim.
Each worker records what `mono_thread_current()` returned at attach and
re-compares on its own thread after every restore - it has to be the worker's own
thread, because the main thread's answer says nothing about anyone else's.
MEASURED: 120 checks across 30 restores, none null, none returning a different
thread.

Counters only on the worker side; the main thread does all the printing. A worker
must never touch stdio - that is how this harness crashed itself once already.

**1c. A pinned managed object survives with its contents intact.** A handle taken
before the first save, so that the object and the handle table are both inside
every snapshot, compared by *contents* rather than by pointer because a non-null
pointer to rubbish is the failure worth catching. MEASURED: 30 of 30 resolved
with correct contents.

**1d. A full collection completes.** `mono_gc_collect(mono_gc_max_generation())`.
The heaviest question available: Boehm scans every attached thread's stack using
bounds registered at attach time, then every heap section and mark bit. Chosen
because two faults inside Mono have written to the stack pointer with its low 32
bits cleared, which is what scanning a wrong stack range looks like.

An intervention rather than an observation, so it also runs once before the first
save. MEASURED: 31 collections per run complete, 166-190 us for the control and
up to 669 us after a restore.

The first version of this oracle reported "0 ms" for all 31 collections, which is
also exactly what a call that does nothing prints. It now reports microseconds
and the used size either side, and the control shows 336 KB going to 328 KB - so
the collector really marks and really sweeps. This is rule two of this document
catching its own author.

Honest limit: the managed heap here is 328 KB to 1 MB. OSFE's is vastly larger,
so a collection that survives in the harness is much weaker evidence than the
same result would be in the game.

**1e. JIT'd managed code runs and returns the right answer.** `Int32.Parse` taken
down both paths through `mono_runtime_invoke`: on rubbish it must come back as a
`FormatException` object, and on "1234567" it must return 1234567 unboxed. The
throwing path is the only test the unwind-table replay has ever had - a wrong
replay does not crash, it breaks managed exception handling, which is invisible
unless something deliberately throws. MEASURED: 31 throws of the right type and
31 correct return values per run, and the same before any save as the control.

**What all five together say.** In runs that die, they die with every one of these
green. Mono's JIT bookkeeping, its thread-local state, its handle table, its
collector and its exception machinery all survive a restore intact. Combined with
the heap validating clean, that removes the entire managed runtime from suspicion
and leaves the failure somewhere none of these oracles can see.

### 2. Every heap's own metadata is self-consistent - BUILT, PASSES, AND THAT IS THE RESULT

`HeapValidate` on every heap, immediately after the restore loop and before any
thread is resumed. It walks the allocator's structures using the allocator's own
rules, so it needs no offsets and no knowledge of the heap format.

This is aimed directly at the current failure. The fault is a write into
ucrtbase's read-only image reached from `sprintf`, with `RtlAllocateHeap` in the
same call chain and Mono as the caller - which reads as the allocator handing out
something that was never a heap block, i.e. a free list containing garbage. A
heap is not cleanly on one side of the boundary: its segments are in the
snapshot, but the low-fragmentation heap keeps per-thread caches reachable from
the TEB, and TEBs are not. That is Class B, and it fits the eight TEB-held blocks
already in the logs.

Either outcome is worth the build. A failure names the seam. A pass clears the
heap and forces the search somewhere I have not looked, which given the record
above is the more valuable of the two.

MEASURED, and it is the second outcome. Five heaps validate clean *before every
save* and *after every restore*, across a batch in which five of six runs went on
to die. Cost is 0.1 ms at save and 0.4-0.6 ms after a restore, so the cost risk
was unfounded at harness scale and the check can stay on (`D3D9SW_HEAPCHECK=0`
disables it). The save-time control is what makes the after-restore pass mean
anything: the heap was not already broken.

So the allocator's bookkeeping is not corrupt, and the story I told for signature
383 - "the heap hands out something that was never a block" - is wrong as stated.
What is being handed around is bad *contents*, not bad heap structure.

The fault sites that arrived with a validated heap say the same thing in three
voices, and all three are now named:

- `ntdll!RtlEnterCriticalSection+0x4a`, with `rcx` - the `CRITICAL_SECTION *`
  argument - holding an address inside ntdll's own code.
- `ucrtbase!output_processor::process+0x74`, the `sprintf` state machine again.
- `ntdll!RtlpWakeByAddress+0x1fc` writing through a null structure at offset
  0x18. This is the SRWLOCK and condition-variable wake path, i.e. exactly the
  class flagged as unhookable in invariant 3.

Twice now a pointer that should address data has instead addressed a *module
image* - ntdll's code where a lock should be, ucrtbase's image where a format
buffer should be. That pattern is worth more than any individual crash, and it is
not something a heap walk can see.

One further observation, recorded because it is arithmetic rather than
interpretation: two faults at `mono-2.0-bdwgc+72579` wrote to `0x2200000000` and
`0xDE00000000` while the faulting thread's `rsp` was `0x22AFBFF5C8` and
`0xDE25FFF938`. In both cases the write target is the stack pointer with its low
32 bits cleared. A pointer derived from a stack address that has lost its low
half, in two independent runs, is not a coincidence - but no mechanism is
proposed here, because proposing one before measuring is the failure mode this
document exists to stop.

### 3. No lock is left held by a thread that will never release it

Partly built (critical sections, class B coverage thin). The correct post-restore
value of every lock is *free*, not its recorded value, because the thread that
would have released it has been rewound past the release.

Open and unsolved: SRWLOCKs and condition variables are initialised by
assignment, so there is no call to hook and no way to record them the way
sections are recorded. An earlier harness fault named
`ntdll!RtlpWakeByAddress+0x15a`, so they are not hypothetical. Clearing the held
bit by scanning is guesswork and is not proposed.

### 4. Every thread the restored state refers to still exists

A restore has reported 52 contexts against 55 recorded at save. Three threads
that existed at save time had exited, so restored state refers to threads that
are gone - and a structure whose writer is gone is a structure that will never be
completed. This is the missing second ingredient for the Class C instance above.

Cheap to check: compare the recorded thread set against the live one and report
the difference. Currently the counts are logged but never compared.

### 5. No structure with a head outside the snapshot has entries inside it

The general form of the unwind-table bug, and a search rather than a check.
Candidates by shape: loader lists, TLS bookkeeping, RPC and COM tables, the
critical-section list ntdll itself maintains. Any structure whose head lives in a
held module and whose entries live in a rewound heap has the identical failure
mode, and there is no reason to expect the unwind tables are the only one.

## Two rules for anything added here

**Express invariants through exported functions, never struct layouts.** The
jit-info check works because it asks Mono a question Mono answers. The moment a
chunk-array offset is hard-coded, the check rots silently at the next Unity
version - and a rotted invariant does not go quiet, it produces confident wrong
answers, which is worse than having no check at all.

**A check that has never failed is not yet a check.** Every mechanism here that
reports zero should be made to report non-zero at least once, deliberately, before
its silence is treated as evidence. The critical-section tracking reported "0
tracked" for an entire session because of a rate limiter, and looked exactly like
a clean result.
